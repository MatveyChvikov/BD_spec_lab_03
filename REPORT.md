## 1. Исходные данные

### 1.2 Объём данных

> Примечание: при фиксированном `setseed(0.42)` число позиций на заказ в среднем даёт ~1 строку на заказ в `order_items` (детерминированное распределение `random()`).

Замеры выполнялись с параметрами из скриптов: `SET max_parallel_workers_per_gather = 0`, `SET work_mem = '32MB'`, предварительный `ANALYZE`.

## 2. Найденные медленные запросы (до оптимизации)

### Запрос №1 — последние заказы пользователя

SQL: выборка заказов по `user_id` (первый пользователь по `email`), сортировка по `created_at DESC`, `LIMIT 100` (см. `sql/02_explain_before.sql`).

План (ключевое): `Seq Scan on orders` с фильтром `user_id = $0`, снято 99 989 строк, затем сортировка по памяти.

Execution Time: 4.435 ms

Почему медленно: нет индекса по `(user_id, created_at)` — полный проход по `orders` и сортировка малого результата поверх большого скана.

---

### Запрос №2 — выручка по оплаченным за год

SQL: `COUNT` и `SUM(total_amount)` для `status = 'paid'` и диапазона дат `[2024-06-01, 2025-06-01)`.

План: `Seq Scan on orders` с составным фильтром по дате и статусу, отброшено 75 061 строк.

Execution Time: 8.364 ms

Почему медленно: нет подходящего составного индекса `(status, created_at)` — чтение всей таблицы.

---

### Запрос №3 — топ товаров по выручке (JOIN + GROUP BY)

SQL: соединение `order_items` и `orders`, фильтр по году заказа, `GROUP BY product_name`, `ORDER BY sum(subtotal) DESC LIMIT 25`.

План: `Hash Join` + `Seq Scan` на обеих таблицах (`~100k` строк в `order_items`, `~50k` отфильтрованных заказов).

Execution Time: 38.810 ms

Почему медленно: нет индекса по `order_items.order_id` для быстрого join и нет индекса по `product_name` для агрегирования; ветка по `orders` остаётся сканом по дате.

---

### Запрос №4 (опционально) — помесячная агрегатика по всем заказам

SQL: `date_trunc('month', created_at)`, `COUNT`, `AVG` по всей таблице `orders`.

План: `Seq Scan` → `Sort` → `GroupAggregate` по выражению от `created_at`.

Execution Time: 38.518 ms

Почему медленно: нужен полный проход и сортировка/группировка по производному столбцу; одним только B-tree по сырому `created_at` это не сводится к «дешёвому» плану на 100k строках без переписывания запроса (например, материализованное представление).

## 3. Добавленные индексы и обоснование типа

Все индексы создаются в `sql/03_indexes.sql`.

### Индекс №1

- SQL: `CREATE INDEX idx_orders_user_created_at ON orders (user_id, created_at DESC);`
- Какой запрос ускоряет: Q1 (фильтр по пользователю и сортировка по дате).
- Почему BTREE: классическое равенство по лидирующему столбцу + упорядочивание по второму; `DESC` совпадает с `ORDER BY created_at DESC`.

### Индекс №2

- SQL: `CREATE INDEX idx_orders_status_created_at ON orders (status, created_at);`
- Какой запрос ускоряет: Q2 (равенство `status` + диапазон по `created_at`).
- Почему BTREE: типичный шаблон «код статуса + временной интервал»; bitmap-сканирование по этому индексу хорошо сочетается с селективностью `status = 'paid'`.

### Индекс №3

- SQL: `CREATE INDEX idx_order_items_order_id ON order_items (order_id);`
- Какой запрос ускоряет: Q3 (соединение по `order_id`).
- Почему BTREE: точное соответствие FK/join-ключу; альтернатива hash-индекс в PostgreSQL ограничена и редко нужна здесь.

### Индекс №4

- SQL: `CREATE INDEX idx_order_items_product_name ON order_items (product_name);`
- Какой запрос ускоряет: Q3 (`GROUP BY product_name`).
- Почему BTREE: равенство/группировка по текстовому каталогу товаров; для очень больших текстов рассматривали бы нормализацию до `product_id`, здесь достаточно BTREE по имени.

### Индекс №5 (BRIN)

- SQL: `CREATE INDEX brin_orders_created_at ON orders USING brin (created_at);`
- Какой запрос ускоряет: потенциально широкие фильтры/сканы по времени на append-подобных данных.
- Почему BRIN: компактный индекс по физической близости строк на диске; выгоден для больших объёмов при сканах по диапазону дат, когда не нужна точечная уникальность.

## 5. Партиционирование `orders` по дате

### 5.1 Стратегия

Декларативное партиционирование `RANGE (created_at)` по месяцам, партиции с `2023-12-01` по `2027-03-01`, плюс `DEFAULT` для любых выбросов за пределами сетки.

Первичный ключ партиционированной таблицы: `PRIMARY KEY (id, created_at)` (требование PostgreSQL для уникальности на родителе).

### 5.2 Реализация

Скрипт `sql/05_partition_orders.sql`:

1. В `order_items` и `order_status_history` добавлен столбец `order_created_at`, backfill из `orders.created_at`.
2. Триггеры `BEFORE INSERT` подставляют `order_created_at` из родительской строки `orders`, если значение не задано (совместимость с приложением).
3. Сняты FK на старую `orders`, таблица переименована в `orders_old`, создана новая `orders` с `PARTITION BY RANGE (created_at)`, данные перелиты `INSERT … SELECT`, `orders_old` удалена.
4. Восстановлены составные внешние ключи `(order_id, order_created_at) → orders(id, created_at)`.
5. Созданы индексы: `idx_orders_id (id)` для точечных запросов по `id`, повторены пользовательские индексы и BRIN.

### 5.3 Проверка эффекта

- Q2 после партиции: план с `Append` только по месяцам, попадающим в диапазон `[2024-06, 2025-06)` — видно отсечение партиций вместо одного seq scan всей таблицы.
- Q4: вместо одного seq scan — `Append` по месячным партициям с тем же итоговым числом строк.
- Доп. запрос в `06_explain_after_partition.sql`: подсчёт заказов за один календарный месяц — узкий `Append` и низкое время (~0.51 ms в замере).

## 6. Итоговые замеры (три состояния)

Сводка Execution Time из `EXPLAIN (ANALYZE, BUFFERS)`:

| Запрос | До индексов | После индексов | После партиционирования |
| Q1 | 4.435 ms | 0.063 ms | 0.678 ms |
| Q2 | 8.364 ms | 5.691 ms | 6.836 ms |
| Q3 | 38.810 ms | 35.455 ms | 41.373 ms |
| Q4 | 38.518 ms | 36.384 ms | 36.476 ms |

Интерпретация: индексы дали максимальный выигрыш на «точечных» шаблонах Q1–Q2. После партиционирования Q1 стал медленнее, чем с одними только индексами: фильтр только по `user_id` не содержит ключа партиционирования, планировщик обходит много партиций (много дешёвых seq scan по ~0 ms, но заметный рост planning time). Q3 слегка ухудшился из‑за накладных расходов `Append` и большего числа буферных чтений при том же hash join. Q2 и Q4 остаются в том же порядке величин; для Q2 выигрыш от партиций проявляется в структуре плана (pruning), а не только в миллисекундах на 100k строках.

## 7. Что удалось исправить

1. Убран полный скан `orders` в Q1 за счёт составного BTREE `(user_id, created_at DESC)`.
2. Снижен объём чтения в Q2 за счёт BTREE `(status, created_at)` и bitmap-сканирования.
3. Подготовлена почва для Q3 индексами по `order_id` и `product_name` (частичный выигрыш; узкое место переносится к агрегированию).
4. Внеднено месячное партиционирование `orders` с сохранением целостности через составной FK и триггеры для дочерних таблиц.
5. Ускорен seed: при массовой вставке `order_items` временно отключается триггер пересчёта `total_amount`, затем выполняется один пакетный `UPDATE` (см. `sql/01_seed_100k.sql`).

---

## 8. Что не удалось исправить только индексами

1. Q3: hash-агрегация по ~2000 значениям `product_name` при почти полном скане `order_items` — индексы не меняют фундаментальную стоимость чтения всех строк и построения хэш-таблицы; для существенного ускорения нужны денормализация/предрасчёт (materialized view, OLAP-слой) или сужение набора данных.
2. Q4: `GroupAggregate` по `date_trunc(month, created_at)` на всей таблице — индекс по сырому `created_at` не даёт план «index only» для группировки по функции без generated column / expression index на `date_trunc('month', created_at)` или без переписывания запроса (rollup-таблица по месяцам).
3. BRIN по `created_at` в данных объёма 100k не сменил выбранный план для Q2/Q4 в нашем замере: оптимизатор предпочёл bitmap по BTREE `(status, created_at)` — BRIN остаётся запасным инструментом на больших объёмах и «широких» временных срезах.

---

## 9. Выводы

1. `EXPLAIN (ANALYZE, BUFFERS)` — основной источник правды: видно и Seq Scan, и Rows Removed by Filter, и реальное время.
2. Индексы проектируются под конкретные предикаты и сортировки: составной BTREE для `(user_id, created_at)` и `(status, created_at)` окупается сразу.
3. Партиционирование без ключа партиции в запросе не гарантирует ускорения; для фильтра только по `user_id` оно даже ухудшило время из‑за обхода многих дочерних отношений.
4. Тяжёлые агрегаты (Q3, Q4) требуют либо изменения модели данных, либо предрасчёта, а не только добавления индексов.
5. Сопровождение партиций в PostgreSQL требует продумать PK/FK: для ссылок на партиционированную таблицу часто нужен составной ключ и денормализация `created_at` в дочерние строки.
